# Layout selection by job, not by trend

Ask: What object is primary? What does user repeat? Does the user compare records or edit one object? Is contextual preview essential? Is the system navigationally broad?

| Job pattern | Default composition | When NOT to choose |
|---|---|---|
| Single-purpose utility | focused primary surface + compact options + preview/output | many equal modules need navigation |
| Collection navigation | sidebar/tree + responsive list, optional inspector | flat simple form |
| Record processing | filters/action bar + wide table/list + drawer; batch affordances | narrative editorial content |
| Editor/workbench | main canvas/editor + tool strip + inspector; resizable panes | infrequent simple input |
| Multi-step form | progressive sections, contextual validation, save state | power-user mass editing |
| Preferences/settings | category selector + compact labeled controls | actionable data workflow |
| Analytics | question/KPI → trend/segment → underlying evidence | pure decoration / no drill-down |
| Monitoring | state/change summary + sortable event list + context | faux real-time animation without data |
| Detail review | selected object summary + sections/tabs + next/previous | single-click simple readout |

## Mandatory reasoning output (short)

- Primary user question: `...`
- Primary object: `...`
- Frequency/density: `...`
- Pattern selected: `...` because `...`
- Primary action and the next visible state: `...`
- Competing pattern rejected: `...` because `...`

A dashboard is only appropriate when decisions require summary metrics; **not** the default for every new project. A split workspace is appropriate when selection-context continuity materially improves work, not just because Finder looks attractive.
